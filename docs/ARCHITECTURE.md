# 구조와 설계 배경

`CLAUDE.md` 가 "무엇을 조심해야 하는지"라면, 이 문서는 **"왜 이렇게 만들었는지"** 입니다.

---

## 1. 전체 그림

```
                       ┌──────────────┐        ┌──────────────┐
   사용자 입력  ───────▶│   cli.py     │        │   gui.py     │◀─── 마우스
   (명령줄 인자)        │ argparse     │        │ tkinter      │
                       └──────┬───────┘        └──────┬───────┘
                              │                       │
                              └───────────┬───────────┘
                                          ▼
                                  ┌───────────────┐
                                  │  config.py    │  기본값 < 파일 < 환경변수 < 인자
                                  └───────┬───────┘
                                          ▼
                                  ┌───────────────┐
                                  │  runner.py    │  TunnelSession
                                  │  실행 엔진     │  검증→준비→시작→감시→정리
                                  └───┬───┬───┬───┘
                        ┌─────────────┘   │   └──────────────┐
                        ▼                 ▼                  ▼
                ┌──────────────┐  ┌──────────────┐   ┌──────────────┐
                │ binaries.py  │  │ providers/   │   │ firewall.py  │
                │ 실행파일 확보 │  │ 터널 프로세스 │   │ 규칙 적용/원복│
                └──────────────┘  └──────┬───────┘   └──────────────┘
                                         ▼
                                  ┌──────────────┐
```

핵심은 **`runner.py` 의 `TunnelSession`** 입니다. CLI 와 GUI 는 이 클래스를 부르는 껍데기일 뿐입니다.

## 2. 왜 이렇게 갈랐나

### CLI 와 GUI 가 같은 엔진을 쓴다

처음에는 `cli.py` 의 `cmd_run()` 안에 모든 흐름이 있었습니다. GUI 를 붙이면서
같은 로직을 복사할 뻔했고, 그러면 한쪽만 고치는 버그가 반드시 생깁니다.
그래서 `TunnelSession` 으로 뽑아내고 `cmd_run()` 은 이걸 호출하도록 다시 썼습니다.

세션의 각 단계는 **독립적으로 호출 가능**해야 GUI 가 쓸 수 있습니다.
CLI 는 순서대로 쭉 부르고, GUI 는 작업 스레드에서 같은 순서로 부르되
사이사이에 화면을 갱신합니다.

### 예외는 `SessionError(메시지, 힌트)` 로 통일

사용자에게 보여줄 오류와 프로그래밍 실수를 구분하기 위해서입니다.
`SessionError` 는 그대로 화면에 뿌려도 되는 한국어 메시지 + "그래서 뭘 하면 되는지" 힌트를 가집니다.
CLI 는 stderr 에, GUI 는 오류 대화상자에 같은 내용을 씁니다.

### 로그는 sink 구조

`util.info/ok/warn/error` 는 콘솔에 쓰는 동시에 등록된 콜백(sink)에도 보냅니다.
GUI 는 sink 를 하나 등록해서 로그 창에 실시간으로 흘립니다.
덕분에 GUI 전용 로깅 코드를 따로 만들 필요가 없고, 라이브러리 코드는 GUI 존재를 모릅니다.

`pythonw.exe` 로 실행하면 `sys.stdout` 이 `None` 이라 `print()` 가 터집니다.
그래서 모든 출력은 `util._write()` 를 거칩니다.

## 3. 모듈별 설계 메모

### config.py — 4단 병합

```
DEFAULTS  <  설정 파일  <  환경 변수  <  명령줄 인자 / 화면 입력
```

- 설정 파일 탐색: `./fastunnel.json` → `~/.fastunnel/config.json` (먼저 찾은 하나만)
- `load()` 는 파일에서 읽어 올 때, `from_dict()` 는 이미 가진 값으로 만들 때 씁니다.
- GUI 는 **파일을 다시 읽지 않고** 메모리 값 + 화면 값을 합칩니다.
  안 그러면 대화상자에서 방금 입력한 토큰이 저장 전이라는 이유로 사라집니다. (실제로 났던 버그)
- 알 수 없는 키도 버리지 않고 보존합니다(앞으로 늘어날 설정 대비).

### binaries.py — 설치를 "없애는" 모듈

사용자가 cloudflared 를 직접 설치하지 않아도 되게 만드는 게 목적입니다.

우선순위: `--bin` 명시 경로 → `~/.fastunnel/bin/` → 시스템 PATH → 없으면 다운로드

- **시스템 PATH 에 있는 것은 임의로 갱신하지 않습니다.** 사용자가 직접 관리하는 것이므로.
- `~/.fastunnel/bin/` 에 우리가 받은 것만 업데이트 대상입니다.
- 최신 버전 확인은 GitHub API 이고 결과를 24시간 캐시합니다(`state/version-cache.json`).
  오프라인이어도 실패하지 않고 기존 파일로 진행합니다.
- ngrok 은 자체 `ngrok update` 명령이 있어서 그걸 씁니다.

### providers/ — 제공자마다 다른 "주소 알아내는 법"

두 제공자는 구조가 꽤 다릅니다.

|  | cloudflared | ngrok |
|---|---|---|
| 프로세스 | **포트마다 1개** | 전체 **1개** |
| 주소 얻는 법 | 프로세스 출력에서 정규식으로 추출 | 로컬 관리 API(`127.0.0.1:4040/api/tunnels`) 폴링 |
| 설정 | 명령줄 인자 | YAML 파일 생성 후 `--config` |
| 인증 | 불필요 | authtoken 필수 |

공통 인터페이스는 `BaseProvider`(`preflight`/`start`/`poll`/`stop`)와 `Tunnel` 입니다.
`poll()` 은 **1초마다 불리므로 절대 예외를 던지면 안 됩니다.** 감시 루프가 죽습니다.

cloudflared 출력 파싱은 스레드에서 합니다. 프로세스마다 리더 스레드 1개가
stdout 을 읽어 로그 파일에 쓰고 URL 정규식을 검사한 뒤 `threading.Event` 로 알립니다.

### firewall.py — "추가한 것만 되돌린다"

원칙: **우리가 넣은 규칙만 지운다.** 사용자가 원래 갖고 있던 규칙은 절대 건드리지 않습니다.

- 규칙마다 "되돌리는 명령"을 같이 만들어 두고(`plan()` 이 add/remove 쌍을 반환),
  적용에 성공한 것만 `applied` 에 쌓아 종료 시 역순으로 실행합니다.
- 그 목록을 `state/firewall-<pid>.json` 에도 저장합니다. 강제 종료로 프로세스가 죽어도
  `firewall cleanup` 이 파일을 읽어 정리할 수 있습니다.
- 연속 포트는 범위 규칙 하나로 묶습니다(`8000-8010` → 규칙 2개면 충분).
- 백엔드 자동 감지: Windows=netsh / Linux=ufw→firewalld→iptables / macOS=없음.
  ufw 가 설치돼 있어도 비활성이면 규칙을 넣지 않습니다(넣어봐야 의미 없음).

### notify.py — 실패해도 조용히

알림은 **부가 기능**입니다. 전송 실패로 터널이 멈추면 안 됩니다.
그래서 모든 전송은 예외를 잡아 경고만 남기고, 429(레이트리밋)는 `retry_after` 만큼 기다려 최대 3회 재시도합니다.

설정 파일의 자리표시자(`<ID>`, `<TOKEN>`)를 실제 URL 로 착각해 요청을 보내는 일이 있어서
`_valid_url()` 로 걸러냅니다.

### gui.py — 스레드 경계가 전부

```
   [메인 스레드]                       [작업 스레드]
   위젯 · 대화상자                     TunnelSession 실행
        ▲                                    │
        │   self.events (queue.Queue)        │
        └────────────────────────────────────┘
              _drain_events() 가 120ms 마다 비움
```

tkinter 위젯을 작업 스레드에서 만지면 조용히 깨지거나 뻗습니다.
그래서 작업 스레드는 **큐에 넣기만** 하고, 화면 갱신은 전부 메인 스레드에서 합니다.
`util` 로그 sink 도 작업 스레드에서 불리므로 마찬가지로 큐에만 넣습니다.

예외 처리 계층:

| 계층 | 처리 |
|---|---|
| 입력 검증 | `on_start()` 에서 즉시 경고, 시작 안 함 |
| 작업 스레드 | `_run_session()` 이 전부 잡아 `fatal` 이벤트로 전달 → 오류 창 + 버튼 복구 |
| tkinter 콜백 | `report_callback_exception` 재정의 → 로그 + 파일 기록 + 창 유지 |
| 그 외 스레드 | `threading.excepthook` → 로그 기록 |
| 창 생성 자체 실패 | `launch()` 가 잡아 `logs/gui-error.log` 기록 후 메시지 |

## 4. 파일이 놓이는 곳

```
~/.fastunnel/                     (FASTUNNEL_HOME 으로 변경 가능 - 테스트가 이걸 씁니다)
├── bin/                          내려받은 cloudflared / ngrok
├── state/
│   ├── tunnels.json              현재 열린 터널 정보
│   ├── firewall-<pid>.json       추가한 방화벽 규칙과 되돌리는 명령
│   ├── version-cache.json        최신 버전 확인 캐시(24시간)
│   ├── gui.lock                  GUI 중복 실행 감지용 PID
│   └── ngrok-<pid>.yml           ngrok 설정(종료 시 삭제)
└── logs/
    ├── cloudflared-<pid>.log     터널 프로세스 원본 출력
    └── gui-error.log             GUI 예외 추적
```

## 5. 의도적으로 하지 않은 것

| 안 한 것 | 이유 |
|---|---|
| 외부 패키지 사용 | "복잡한 설치 없이"가 핵심 요구사항이었습니다 |
| 시스템 트레이 아이콘 | 표준 라이브러리로는 불가능. pystray 를 넣으면 제약 1번 위반 |
| 서비스/데몬 등록 | 임시 터널이 목적. 상시 운영은 cloudflared 정식 터널이 맞습니다 |
| 터널 주소 고정 | quick tunnel 은 매번 바뀝니다. 고정하려면 도메인 + 계정 필요 |
| firewalld 아웃바운드 | firewalld 는 기본적으로 아웃바운드를 막지 않습니다 |
| 방화벽 규칙 영구 저장 | 기본은 임시. `--firewall-persist` 로 선택 가능하게만 |
